## Clarifications

### Session 2026-08-18

- Q: 质量门禁的配置在 v0.4 应绑定到什么粒度? → A: 项目默认配置 + TeamRun 启动时临时覆盖(不落盘为模板);Workflow 模板绑定推迟到 v0.5。
- Q: 门禁失败时,豁免权限应如何划分? → A: 主 Agent 全权豁免——可豁免任意失败项(含高风险),不设人工拦截;但豁免必须逐项、附理由、留痕审计,用户保留随时复审豁免记录与接管运行的权利。
- Q: Review Center 应以什么形态存在? → A: 全局审查中心——侧边栏新增顶级入口,聚合全部运行中等待审查的任务作为审查主战场;运行详情保留任务上下文跳转,与 v0.3 工作台「等待审查」分区呼应。
- Q: 外部平台回灌(P4 可选项)首发应支持哪个平台范围? → A: 仅 GitHub(PR 创建、CI 状态、Review 评论回灌);多平台抽象推迟到 v0.6 集成体系。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Diff 审查工作台(Review Center)(Priority: P1)

审查者(用户或主 Agent)在应用内完成任务审查:主战场是侧边栏新增的全局
Review Center,聚合全部运行中等待审查的任务(与 v0.3 工作台「等待审查」
分区呼应;运行详情保留上下文跳转)。在审查中心内,以文件变更树浏览完整
Diff,
支持基线 / 当前工作树 / 集成结果三方对比;对任意行添加评论,并可勾选多条评论
一次性生成返工(评论自动带入返工任务上下文);报告、执行日志、Diff 与测试
证据相互联动跳转;对高风险文件、敏感文件、超大 Diff 与越界修改给出醒目提示;
提供未解决发现(unresolved findings)清单;集成前可预览合并冲突并走处理
流程;审查结束生成结构化交付摘要(结论、证据、遗留项)。

**Why this priority**: 把「Agent 说完成了」升级为「结果有证据、可安全交付」
是本版本的核心目标;Diff 工作台是一切审查与门禁的载体,roadMap 推荐顺序中
位列第 2。

**Independent Test**: 对一个含 3 个写任务的真实运行,在界面内完成查看 Diff →
行级评论 → 批量返工 → 复审 → 集成的全流程,全程不打开终端。

**Acceptance Scenarios**:

1. **Given** 一个已完成写任务,**When** 审查者打开审查视图,**Then** 呈现
   文件变更树与完整 Diff,并可切换基线/工作树/集成结果三方对比。
2. **Given** 审查者在两处不同文件留下行级评论,**When** 提交批量返工,
   **Then** 生成一个返工任务,两条评论及位置进入返工上下文,复用同一子
   Agent 会话。
3. **Given** 任务修改了数据库迁移文件或超出授权目录,**When** 打开 Diff,
   **Then** 显示高风险/越界提示,且该发现进入未解决清单直至处理。
4. **Given** 集成会产生冲突,**When** 审查者选择集成,**Then** 先展示冲突
   预览与处理选项,未确认前不执行集成。
5. **Given** 审查者结束审查,**When** 选择通过,**Then** 生成结构化交付
   摘要(结论、证据链接、遗留项)并入档。

### User Story 2 - 自动质量门禁(Priority: P2)

用户可为项目或 Workflow 配置 PASS 前置条件,例如:必要测试/lint/类型检查/
构建通过;不存在未处理的高风险发现;修改范围未超出允许目录;所有依赖任务
已接受;目标分支仍处于安全基线;必要 Reviewer 已通过;数据库迁移、安全配置
等高风险变更已人工确认;已知 Todo、评论与阻塞项清零。门禁执行结果输出明确的
通过项、失败项与豁免记录——不是布尔值;失败时能准确说明原因,并把修复意见
回传到原会话(返工上下文)。

**Why this priority**: 门禁把审查经验固化为可重复的机器检查,是「可交付性」
的保障,也是跨模型审查仲裁的判定基础。

**Independent Test**: 为示例项目配置含 4 项条件的门禁,分别构造满足/违反
场景,验证结果明细、豁免记录与失败意见回传。

**Acceptance Scenarios**:

1. **Given** 门禁含「必要测试通过」与「无未处理高风险发现」两项,**When**
   某任务测试失败且存在一条未处理高风险评论,**Then** 门禁结果列出两项失败
   及原因,PASS 被阻止。
2. **Given** 某项条件经用户显式豁免并填写理由,**When** 门禁执行,**Then**
   该项记为豁免(非通过),豁免人与理由入档,其余项照常判定。
3. **Given** 门禁失败,**When** 结果回传,**Then** 原会话收到可执行的修复
   意见(哪项、为什么、建议动作),而不是笼统的「未通过」。
4. **Given** 目标分支在审查期间发生移动,**When** 门禁执行,**Then** 基线
   安全项判失败并说明基线变化。

---

### User Story 3 - 跨模型审查与仲裁(Priority: P3)

支持内置审查模式:Claude 实现、Codex 审查;Codex 实现、Claude 审查;两个
只读 Agent 独立调查后主 Agent 综合;多 Agent 并行出方案再由测试与审查者
选择;安全/架构/测试等角色分别审查;高风险任务多 Reviewer 仲裁。结论冲突时,
输出「共识 / 分歧 / 待验证项」三段结构,而不是强行合并为单一结论。

**Why this priority**: 跨模型互查显著提升真实缺陷发现率,并让「谁审查、依据
什么」可追溯;但其价值依赖前两个故事提供的证据与门禁基础。

**Independent Test**: 对同一任务分别启用「Claude 实现 Codex 审查」与
「双只读独立调查」模式,验证结论结构与冲突呈现。

**Acceptance Scenarios**:

1. **Given** 任务由 Claude 实现,**When** 启用 Codex 审查模式,**Then**
   审查任务自动派发给只读 Codex,结论回流至原任务审查视图。
2. **Given** 两个只读 Agent 调查结论部分冲突,**When** 综合结论生成,
   **Then** 以共识/分歧/待验证项三段呈现,分歧不丢失。
3. **Given** 高风险任务配置双 Reviewer 仲裁,**When** 两者结论一致/不一致,
   **Then** 分别给出仲裁通过与显式分歧记录,不一致时默认不自动通过。

---

### User Story 4 - 外部平台回灌(可选)(Priority: P4)

支持在 GitHub 创建 PR、展示 CI 状态、回收 Review comment 与检查结果到应用内
审查视图。首发仅支持 GitHub,多平台抽象随 v0.6 集成体系引入。默认关闭;启用
需要用户显式配置 GitHub 凭证,凭证按宪法安全默认存储与使用。

**Why this priority**: 与现有工程流程衔接有价值,但依赖外部平台与网络,
属增量集成,不应阻塞核心审查闭环。

**Independent Test**: 配置示例仓库凭证后创建 PR,验证状态与评论回灌展示。

**Acceptance Scenarios**:

1. **Given** 已配置外部平台凭证且任务通过审查,**When** 用户选择创建 PR,
   **Then** PR 建立并与该任务关联,链接可在审查视图打开。
2. **Given** 关联 PR 有新的检查结果或评论,**When** 用户刷新,**Then**
   状态与评论回灌展示,并与本地证据并列。

### Edge Cases

- 超大 Diff(数千行、二进制或生成文件)→ 变更树必须可分页/折叠,二进制给
  出摘要而非内容,界面不得卡死。
- 敏感文件内容出现在 Diff 中 → 按现有脱敏规则展示,密钥类内容不得明文渲染。
- 行级评论引用的行在返工后消失 → 评论保留原上下文快照,标记「行已变更」,
  不允许静默丢失。
- 门禁条件互相矛盾(如要求 Todo 清零但 Workflow 模板自带 Todo)→ 冲突在
  保存配置时提示,不允许保存永不满足的组合而不警告。
- 豁免滥用(主 Agent 全量豁免绕过门禁)→ 豁免必须逐项、附理由、留痕并
  可审计;交付摘要与审查视图 MUST 醒目呈现豁免清单,用户复审时可对豁免
  提出异议并触发返工。
- 冲突预览与实际集成结果不一致(预览后分支又移动)→ 集成前必须复核基线,
  不一致时终止并回到预览。
- 多 Reviewer 同时给出相反结论且均有证据 → 仲裁记录双方证据与分歧,
  默认走向人工确认而非随机取舍。
- 审查期间任务被取消/丢弃 → 审查会话关闭并留痕,评论不外溢到其他任务。
- 外部平台不可达或凭证失效 → 回灌功能降级为手动刷新+明确错误提示,
  不得影响本地审查与门禁。

## Requirements *(mandatory)*

### Functional Requirements

**Diff 审查工作台**

- **FR-001**: 系统 MUST 提供全局 Review Center(侧边栏顶级入口,聚合全部
  运行中等待审查的任务),并在其中提供文件变更树与完整 Diff 视图,支持
  基线 / 当前工作树 / 集成结果三方对比。
- **FR-002**: 审查者 MUST 能对任意行添加评论,并 MUST 能将多条评论合入一次
  批量返工;返工 MUST 复用原子会话并携带评论位置上下文。
- **FR-003**: 报告、执行日志、Diff 与测试证据 MUST 相互联动可跳转。
- **FR-004**: 系统 MUST 对高风险文件、敏感文件、超大 Diff 与越界修改给出
  显式提示,并纳入未解决发现清单管理。
- **FR-005**: 系统 MUST 在集成前提供合并冲突预览与处理流程;基线不一致时
  MUST 终止集成。
- **FR-006**: 审查结束 MUST 生成结构化交付摘要(结论、证据链接、遗留项)
  并入档。

**自动质量门禁**

- **FR-007**: 用户 MUST 能配置项目级默认 PASS 前置条件,并 MUST 能在启动
  TeamRun 时临时覆盖(覆盖仅对该运行生效、随运行留档,不回写项目默认);
  条件至少支持:
  必要检查(测试/lint/类型检查/构建)通过、无未处理高风险发现、修改范围
  未越界、依赖任务已接受、目标分支处于安全基线、必要 Reviewer 已通过、
  高风险变更人工确认、已知 Todo/评论/阻塞项清零。
- **FR-008**: 门禁结果 MUST 逐项输出通过 / 失败 / 豁免及原因,不允许仅返回
  布尔结论。
- **FR-009**: 豁免 MUST 逐项进行并附豁免理由;主 Agent 拥有全部失败项
  (含高风险项)的豁免权,豁免不设人工拦截,但 MUST 全量留痕(豁免者、
  时间、理由)并可被用户事后复审;失败项 MUST 给出可执行的修复建议。
- **FR-010**: 门禁失败时系统 MUST 将失败原因与修复意见回传原会话作为返工
  上下文。
- **FR-011**: 门禁判定与结果 MUST 与 GUI 审查视图及 MCP 通道行为一致,
  并留有事件证据。

**跨模型审查与仲裁**

- **FR-012**: 系统 MUST 支持内置审查模式:对向实现/审查(Claude↔Codex)、
  双只读独立调查 + 主 Agent 综合、多方案竞赛、分角色审查(安全/架构/测试)、
  高风险多 Reviewer 仲裁。
- **FR-013**: 结论冲突时系统 MUST 输出共识 / 分歧 / 待验证项三段结构;
  仲裁不一致时 MUST 默认不自动通过并转入人工确认。
- **FR-014**: 每条审查结论 MUST 可追溯到来源(哪个 Agent、哪个版本的证据)。

**外部平台回灌(可选)**

- **FR-015**: 系统 MUST 支持为通过审查的任务创建 GitHub PR 并与任务关联;
  PR 的 CI 状态、Review 评论与检查结果 MUST 能回灌展示。首发仅 GitHub。
- **FR-016**: 外部回灌 MUST 默认关闭;启用需显式配置凭证,凭证的存储与
  使用 MUST 符合项目安全默认;外部不可达时 MUST 降级为本地可用 + 明确错误
  提示。

### Key Entities *(include if feature involves data)*

- **审查会话(Review Session)**: 一次任务审查的载体,关联 Diff 视图状态、
  评论、结论与交付摘要。
- **行级评论(Diff Comment)**: 附着于文件与行位置的审查意见,含上下文
  快照,可被批量转为返工。
- **未解决发现(Finding)**: 风险提示与评论的待办聚合,处理完毕前阻止
  相应门禁项通过。
- **质量门禁(Quality Gate)**: 项目/Workflow 级 PASS 条件配置及其每次
  判定结果(通过项/失败项/豁免记录)。
- **审查模式(Review Mode)**: 跨模型审查的编排方式定义(对向、独立调查、
  竞赛、分角色、仲裁)。
- **仲裁结论(Arbitration)**: 多 Reviewer 结论的聚合,含共识、分歧与
  待验证项。
- **交付摘要(Delivery Summary)**: 审查结束生成的结构化结论(判定、证据
  链接、遗留项)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可在应用内完成「Diff 审查 → 行级评论 → 批量返工 → 复审
  → 集成 → 交付摘要」全流程,全程无需终端(以 3 个真实写任务验证)。
- **SC-002**: 每次 PASS 100% 可追溯到测试、审查与 Git 状态证据链。
- **SC-003**: 门禁失败时 100% 输出逐项原因与修复建议,并成功回传原会话。
- **SC-004**: 行级评论 → 返工 → 新 Diff 的闭环成功率 ≥95%(评论不丢失、
  位置可定位)。
- **SC-005**: 仲裁场景 100% 输出共识/分歧/待验证三段结构,无结论被静默合并。
- **SC-006**: 超大 Diff(≥5000 行)场景下审查视图可正常操作,首次呈现
  ≤5 秒。

## Assumptions

- Review Center 基于当前单运行模型即可交付,不前置依赖 v0.3 多 TeamRun;
  集成排队/串行化能力在 v0.3 交付后自动对本版本生效。
- 返工复用原子会话、目标分支安全检查等既有机制沿用现状,不在本规格重定义。
- 「必要检查(测试/lint/类型检查/构建)」指任务工作区内可执行的命令,具体
  命令由用户配置;系统不内置特定技术栈假设。
- 外部平台回灌为可选能力,默认关闭;不阻塞 P1–P3 的交付与验收。
- 可视化 DAG 编辑、Workflow 模板库、上下文治理属 v0.5;质量门禁在 v0.4 绑定
  「项目默认 + TeamRun 临时覆盖」两级,Workflow 级绑定随 v0.5 模板一并引入。
- 凭证、评论、摘要等均按宪法安全默认脱敏与留痕。
