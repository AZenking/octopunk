# Feature Specification: v0.3 稳定性与多任务运行(多 TeamRun / Doctor / 故障恢复 / 资源调度)

**Feature Branch**: `001-v03-stability-multi-teamrun`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "roadmap开始 v0.3, v0.4"(本规格对应 roadMap.md 第 4 节 v0.3;v0.4 另立规格)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多项目并行运行(多 TeamRun)(Priority: P1)

用户(主 Agent 编排者)同时在两个以上仓库各启动一个 TeamRun,各仓库的任务、
worktree、报告与集成互不污染;同一仓库也允许多个 TeamRun 共存,但对目标分支的
集成被串行化,后完成者必须重新核验基线。侧边栏升级为全局工作台,按「正在运行 /
排队等待 / 等待用户输入 / 执行失败 / 等待审查 / 可以集成」汇总所有项目的运行。
并发治理从单一上限升级为三级:全局并发、单项目并发、单 Agent 类型并发。

**Why this priority**: 这是当前最明显的吞吐与使用场景限制(现版本同一时间仅允许
一个活跃 TeamRun),也是 roadMap 推荐实施顺序的第 1 项;解除后其余能力的价值
才能并行兑现。

**Independent Test**: 在 ≥2 个不同仓库同时启动 TeamRun 并各自委派任务,验证
状态、文件与集成结果互不影响;可独立交付并独立演示。

**Acceptance Scenarios**:

1. **Given** 仓库 A 有活跃 TeamRun,**When** 用户在仓库 B 启动新 TeamRun,
   **Then** 两个运行同时推进,B 的启动不因 A 存在而被拒绝。
2. **Given** 同一仓库存在两个已完成的写任务运行,**When** 两者先后执行目标分支
   集成,**Then** 同一时刻至多一个集成动作进行,后到者发现目标分支已移动时
   拒绝集成并提示重新核验。
3. **Given** 全局并发上限为 N 且已达上限,**When** 新任务就绪,**Then** 该任务
   排队并在占用释放后按顺序启动,排队原因可见。

### User Story 2 - 崩溃恢复与故障闭环(Priority: P2)

App 异常退出或被强制结束后重启,能够恢复所有活跃 TeamRun 的状态,重新核对子
Agent 进程的存活情况,并对孤儿进程、孤儿 worktree、临时分支与残留锁给出检测
结果与处理入口。失败按「临时错误 / 配置错误 / 任务错误 / 代码错误 / 系统错误」
分类展示;临时错误在既有自动重试(已上线)基础上,明确显示「是否安全可重试」
与依据;用户可以从失败节点或指定 DAG 节点重新运行,且每次恢复/重试都留下
attempt 与事件证据;禁止静默无限重试。

**Why this priority**: 可恢复、可解释、可审计是产品定位的核心承诺,也是
宪法「持久事实源」原则的直接落地;多 TeamRun 放开后,故障面变大,恢复能力
必须同步跟上。

**Independent Test**: 强制退出 App(含杀死子进程)后重启,验证运行状态完整
恢复、孤儿可检出、失败节点可重跑;可独立交付并独立演示。

**Acceptance Scenarios**:

1. **Given** TeamRun 有 3 个运行中的子任务,**When** App 被强制退出并重启,
   **Then** 重启后运行与任务状态完整呈现,存活子进程被重新关联,已死的子任务
   标记失败并给出恢复选项。
2. **Given** 上次会话残留孤儿 worktree 或临时分支,**When** 用户打开恢复视图,
   **Then** 系统列出残留项及来源运行,并提供安全的清理/保留操作。
3. **Given** 某任务因临时错误失败且重试预算耗尽,**When** 用户查看失败详情,
   **Then** 系统展示错误分类、是否安全重试的判断依据,并提供「从该节点重跑」
   且只重跑受影响路径的操作。

### User Story 3 - 环境诊断中心(Doctor)(Priority: P3)

在 TeamRun 启动前,用户可以主动运行体检,系统检查:各 Agent CLI 的可执行
路径与版本、GUI 进程实际继承的 PATH、CLI 登录与会话可用性、MCP 控制面初始化
与工具发现、Git 仓库/HEAD/分支/脏状态、worktree 创建删除与磁盘空间、沙箱
能力与必要系统权限、Provider 限流/配额/并发额度、数据库健康与迁移版本。
诊断结果包含:可读的失败原因、影响范围、推荐处理方式、可复制的脱敏诊断包,
并支持修复后单项重新检测。start_team 被环境问题注定失败时,应在启动前拦截
并指向诊断结果。

**Why this priority**: PATH、登录、MCP、Git、磁盘等本地细节是当前最大的使用
门槛;把「失败后猜原因」变成「启动前发现」,是多 TeamRun 放量后的安全网。

**Independent Test**: 人为制造 PATH 缺失/未登录/脏工作区等环境问题,运行体检
验证逐项检出与建议质量;可独立交付并独立演示。

**Acceptance Scenarios**:

1. **Given** 终端中 CLI 可用但 GUI 继承的 PATH 不含该 CLI,**When** 用户运行
   体检,**Then** 诊断报告指出差异、影响与修复建议(而非等到任务失败)。
2. **Given** 诊断包被用户复制出去求助,**When** 检查其内容,**Then** 不包含
   密钥、Token 或未脱敏的敏感内容。
3. **Given** 某项检查失败且用户按建议修复,**When** 点击该项重新检测,
   **Then** 仅重跑该项并即时更新结论。

### User Story 4 - 资源感知调度(Priority: P4)

任务启动节奏根据系统负载(CPU/内存/磁盘)与 Provider 并发额度自适应调节;
支持按 Agent 类型限制并发;为交互型任务预留执行槽;排队视图展示每个任务的
排队原因与预计启动顺序;系统压力过高时暂停启动新任务,但不破坏正在运行的
任务,压力回落后自动恢复。

**Why this priority**: 多 TeamRun 放开后,无节流的并发会把失败转嫁为限流与
资源争抢;资源感知是让「能并行」变成「稳定并行」的最后一环。

**Independent Test**: 构造高负载/低配额场景,验证启动自动降速、暂停与恢复、
排队原因可见;可独立交付并独立演示。

**Acceptance Scenarios**:

1. **Given** Provider 并发额度仅剩 1 且两个任务就绪,**When** 调度器启动任务,
   **Then** 仅启动 1 个,另一个展示「等待 Provider 额度」及预计顺序。
2. **Given** 系统处于高压力状态,**When** 有新任务就绪,**Then** 新任务暂缓
   启动且正在运行的任务不受影响;压力回落后自动继续。
3. **Given** 交互型任务在队列中,**When** 并发被批处理任务占满,**Then**
   交互型任务仍能在预留槽位于合理时间内获得执行。

### Edge Cases

- 同一仓库两个运行同时通过核验、先后进入集成(竞态)→ 必须串行化并让后到者
  重新核验基线,不允许双写目标分支。
- 全局/项目/单类型三级并发上限相互矛盾(如项目上限 > 全局上限)→ 生效的
  必须是三者中最严格者,且设置界面明示实际生效值。
- 崩溃恢复时数据库本身损坏或迁移中断 → 恢复流程必须给出数据库健康结论与
  处置建议,而不是静默半恢复。
- 孤儿检测的误判(用户自己开的终端 CLI 进程)→ 只对带 OctoPunk 会话标识的
  进程/工作区判定为孤儿,普通用户进程不得被标记或清理。
- 诊断项超时或 Provider 拒绝配额查询 → 该项标记「无法确认」并说明影响,
  不阻塞其余项,也不默认视为通过。
- 排队任务所属运行被取消/丢弃 → 排队项必须随之移除并留痕,不得稍后复活。
- 磁盘在恢复过程中写满 → 恢复动作必须先做空间预检并给出可读错误,不得损坏
  已有证据数据。

## Requirements *(mandatory)*

### Functional Requirements

**多项目、多 TeamRun**

- **FR-001**: 系统 MUST 允许在不同仓库同时存在活跃 TeamRun,且各运行的
  任务、工作区、报告与事件互不污染。
- **FR-002**: 系统 MUST 允许同一仓库多个 TeamRun 共存,但对同一目标分支的
  集成进行串行化;目标分支已移动或变脏时 MUST 拒绝集成并要求重新核验。
- **FR-003**: 系统 MUST 支持全局并发、单项目并发、单 Agent 类型并发三级
  上限,实际生效值为其中最严格者,且对用户可见。
- **FR-004**: 系统 MUST 提供全局工作台,按「正在运行 / 排队等待 / 等待用户
  输入 / 执行失败 / 等待审查 / 可以集成」汇总全部项目的运行与任务。
- **FR-005**: 用户 MUST 能够对 TeamRun 执行调整排队顺序、暂停与继续操作,
  每次调整 MUST 留有审计记录。

**崩溃恢复与故障闭环**

- **FR-006**: App 重启后系统 MUST 恢复全部活跃 TeamRun 状态,重新核对子
  Agent 进程存活,并对无法关联的任务给出明确失败原因与恢复入口。
- **FR-007**: 系统 MUST 检测孤儿进程、孤儿 worktree、临时分支与残留锁,
  展示其来源,并提供显式的清理/保留操作;清理 MUST 经用户确认。
- **FR-008**: 失败信息 MUST 按临时/配置/任务/代码/系统五类呈现,并明确标注
  「是否安全可重试」及判断依据;禁止静默无限重试。
- **FR-009**: 用户 MUST 能够从失败节点或指定 DAG 节点重新运行,且仅重新
  执行受影响的路径,未受影响的已完成任务不得重复执行。
- **FR-010**: 每次恢复与重试 MUST 记录 attempt 与事件证据,可与原任务关联
  追溯。

**环境诊断中心(Doctor)**

- **FR-011**: 系统 MUST 提供启动前体检,覆盖:CLI 路径与版本、GUI 继承的
  PATH、登录与会话、MCP 初始化与工具发现、Git 仓库状态、worktree 与磁盘
  空间、沙箱与系统权限、Provider 配额、数据库健康。
- **FR-012**: 每个诊断项的结果 MUST 包含失败原因、影响范围与推荐处理方式;
  通过/无法确认/失败三种结论 MUST 可区分。
- **FR-013**: 系统 MUST 能生成可复制的脱敏诊断包,不包含密钥、Token 或
  未脱敏内容。
- **FR-014**: 用户 MUST 能够对单项诊断重新检测;start_team 因环境问题注定
  失败时,系统 MUST 在启动前拦截并指向对应诊断结果。

**资源感知调度**

- **FR-015**: 调度器 MUST 结合系统负载与 Provider 并发额度调节任务启动节奏,
  并支持按 Agent 类型限制并发。
- **FR-016**: 排队视图 MUST 展示每个任务的排队原因与预计启动顺序。
- **FR-017**: 系统压力过高时 MUST 暂停启动新任务且不影响运行中任务,压力
  回落后 MUST 自动恢复调度。
- **FR-018**: 系统 MUST 为交互型任务预留执行槽,避免批处理任务长期独占并发。

### Key Entities *(include if feature involves data)*

- **项目(Project)**: 一个被托管的 Git 仓库及其配置;并发上限与活跃运行的
  归属单位。
- **TeamRun**: 一次编排运行;新增与项目、运行优先级、排队/暂停状态的关联。
- **诊断报告(Doctor Report)**: 一次体检的结果集合,由若干检查项构成,每项
  含结论、原因、影响、建议与检测时间。
- **故障分类(Failure Kind)**: 失败的五类归类及安全重试判定,关联 attempt
  与事件证据。
- **恢复动作(Recovery Action)**: 对孤儿/失败/未完成工作的一次显式处理
  (重跑、清理、保留),全部留痕。
- **资源预算(Resource Budget)**: 全局/项目/单 Agent 类型并发与系统负载、
  Provider 额度共同决定的当前可启动上限。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ≥2 个仓库可同时运行 TeamRun,交叉操作 100 次无状态或工作区
  串扰(0 例跨运行污染)。
- **SC-002**: App 异常退出后重启,100% 的未完成任务呈现可解释状态,且每项
  均有可用恢复入口。
- **SC-003**: 常见环境问题(PATH、登录、MCP、Git、磁盘)在委派前的发现率
  ≥80%(以注入故障样本集计)。
- **SC-004**: 无需打开终端即可完成诊断与恢复的失败占比 ≥80%(以注入故障
  样本集计)。
- **SC-005**: 同仓库多运行场景下,目标分支集成的串行化正确率 100%(无并发
  双写)。
- **SC-006**: 高压场景(资源受限 + Provider 限流)下,运行中任务的失败率
  不因新任务暂停机制而上升,且压力恢复后 5 分钟内调度自动继续。

## Assumptions

- 仍以 macOS 本地单用户场景为边界;远程/多人能力属 v1.0,不在本规格内。
- 子 Agent 仍为 Claude Code、Codex、pi 三类;新增 Provider 的插件化协议属
  v0.6,不在本规格内。
- 已上线的瞬态失败自动重试与启动错峰(提交 0f5d887)作为本规格故障闭环的
  既有基础,不重复设计。
- GUI 与 MCP 共享同一领域状态机(宪法原则二),工作台/诊断/恢复在两条通道
  行为一致。
- 系统负载与 Provider 额度的读取以「尽力而为 + 明示不确定」为原则,不允许
  因探测失败而阻塞调度。
- 跨模型审查、Diff 工作台等审查能力属 v0.4,本规格不包含。
